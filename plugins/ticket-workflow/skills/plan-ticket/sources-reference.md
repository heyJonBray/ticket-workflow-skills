# `.agents/research-sources.md`: field reference

The per-repo config that tells `plan-ticket` and `build-ticket` where research happens. Generated by
`/plan-ticket --setup`; this file documents the schema for writing or editing one by hand.

Keep it in version control. It describes the team's research surface, not one person's machine; use
relative paths like `../acme-api`, never `/Users/you/src/acme-api`.

## Settings block

```yaml
team_prefix: ACME # tracker prefix this repo's issues use
tracker: mcp:linear/acme-workspace # which tracker MCP namespace to read
scout_model: fast-model-name # model to pin on every research subagent
default_mode: guided # guided (pause between milestones) | auto (run straight through)
conventions: [CONTRIBUTING.md, AGENTS.md] # precedence for branch / commit / PR rules
scout_budget: 3 # max scouts launched in parallel
```

`conventions` is highest-authority-first; the first file that answers a question wins. If none of
the listed files exist, the skill asks rather than inventing a house style.

### Per-host values

`tracker` and `scout_model` often differ by host: the same tracker workspace is exposed under
different MCP namespaces, and no model name is valid everywhere. A scalar means "the same
everywhere"; a map keyed by host selects.

```yaml
tracker:
  cursor: mcp:user-linear-acme-workspace
  claude: mcp:linear-acme-workspace
scout_model:
  cursor: composer-2.5
  claude: sonnet
```

`scout_model` should name a fast tier. Scouts do bulk search across many files, not reasoning, and
they are the most frequently launched thing this skill does. If the key is missing the skill asks
once and offers to record the answer.

### Any tracker

`tracker` is whichever issue tracker this repo uses, named by its MCP server. The examples here use
Linear; nothing in the skill depends on it. Jira or another tracker goes in the same slot:

```yaml
tracker: mcp:jira/acme
team_prefix: PROJ # ids are PROJ-123, same shape the skill already expects
```

The skill needs four things from a tracker: read one issue by id, read the issues it relates to,
create an issue, and a `PREFIX-number` id shape. Anything offering those works.

## Source fields

| Field        | Meaning                                                                   |
| ------------ | ------------------------------------------------------------------------- |
| `id`         | stable slug; scouts cite it so the plan can attribute each fact           |
| `group`      | `repo` \| `tracker` \| `external`: sources in one group share one scout   |
| `scout_when` | `always` \| `conditional` \| `never`                                      |
| `trigger`    | plain-English condition the parent evaluates; required when `conditional` |
| `access`     | `mcp:<server>/<tool>` \| `cli:<command>` \| `path:<dir>` \| `url:<base>`  |
| `required`   | `true` means planning **blocks** if the source cannot be reached          |
| `return`     | what the scout must bring back, in this source's own terms                |
| `on_failure` | who to ask, or what to do, when access fails                              |

`never` documents a source you have but deliberately do not scout; it stops the question coming up
again.

A `repo` source is never batched with a `tracker` or `external` one, so `group` controls both what
shares a prompt and what stays isolated.

## Worked example

Prose blurb first (that is what tells a scout _why_ the source matters), then the block.

````markdown
## Sources

### Linear: ACME workspace

Every ticket lives here. The parent reads the primary ticket itself, so this source covers only the
**related** issues it names. Epics carry acceptance criteria that child tickets assume but do not
repeat, so a child ticket alone is often an incomplete spec.

​`yaml id: linear group: tracker scout_when: conditional trigger: the ticket names a parent epic, blocker, or related id whose content matters access: mcp:linear/acme-workspace required: false return: |   For each related id: title, state, how it relates, and the requirements that   change scope or sequencing here. Say whether a blocker is actually done. When   the ticket sits under an epic, return the epic's acceptance criteria, which   child tickets inherit silently. Quote ambiguities verbatim; never resolve them. on_failure: report which ids could not be read; the parent decides whether to gate ​`

### This repo: acme-web

The Next.js client. `CONTRIBUTING.md` owns the commit scope table and is authoritative.

​`yaml id: repo group: repo scout_when: always trigger: access: path:. required: true return: |   Branch state, files and symbols to change, the pattern to copy, what to leave   alone, tests and validation commands, conventions excerpts, the PR template path   and headings, and in-repo spec gaps with verbatim quotes plus paths searched. on_failure: stop and report what could not be read ​`

### acme-api: endpoint contracts

The server repo at `../acme-api`. This repo's API client is generated from it and is routinely a
release behind, so the generated types here are a hint, not the contract.

​`yaml id: api-repo group: repo scout_when: conditional trigger: ticket touches an endpoint, a request/response shape, auth, or client types access: path:../acme-api required: false return: |   The route handler and its DTOs, by path and symbol, with real field names,   optionality, and enum values. Say whether this repo's generated client matches. on_failure: name the endpoint you could not confirm and gate; never guess a shape ​`

### Notion: product specs

Acceptance criteria and copy decks land here before they reach the tracker.

​`yaml id: notion-specs group: external scout_when: conditional trigger: ticket links notion.so, or mentions product copy, empty states, or UX branches access: mcp:notion/search required: false return: |   Verbatim acceptance bullets and the page URL. Quote product copy and policy   language exactly; never paraphrase it. on_failure: ask the product lead for an export; do not plan around a guessed string ​`
````
